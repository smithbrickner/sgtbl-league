# SGTBL — Church Basketball League Platform (prototype)

Static visual prototype for **Smithtown Gospel Tabernacle Basketball League (SGTBL)** — a public-facing league site plus a captain/admin portal. Originally scoped as a **team handball** league (SGTHL); the sport changed to basketball partway through the project. If you see anything referencing handball, goals, goalkeepers, or the old teal/gold branding, it's leftover from before the switch and should be treated as a bug, not a feature.

## Source of truth for rules

Two planning docs live on the Desktop (one level up from this repo):
- `Church_Basketball_League_Structure.docx` — **current**, authoritative rules doc (basketball).
- `Church_Handball_League_Structure.docx` — superseded (handball). Kept for history only; do not implement anything from it that conflicts with the basketball doc.

When in doubt about a rule (scoring, FAAB, trades, playoffs, etc.) — but note the user removed the salary cap on 2026-11-15, which overrides anything the doc says about cap points/salaries/contracts, re-read the basketball doc rather than trusting prior conversation summaries.

## What this is (and isn't)

A **static HTML/CSS/JS prototype** — no backend, no database, no real auth, no payment processing. All data (teams, players, stats, transactions, schedule) is sample/fictional, hand-written into the HTML. The goal is to validate look, feel, and information architecture before committing to a real tech stack.

**Two separate authenticated personas, matching real permission boundaries** (this was a deliberate split, not a shortcut): League Admins run league operations (schedule, scorekeeping, transaction approval, data sync, publishing) and never see a captain's private roster details beyond what they're approving. Captains manage only their own team (roster, weekly availability, trade proposals, FAAB bids, scouting, film) and never see admin-only tools. Don't merge these back into one shared nav — the separation is intentional.

## Design system notes

- Fonts: Barlow Condensed (headings/display) + Inter (body), loaded from Google Fonts.
- Brand palette lives in `tokens.css`. **Gotcha:** the CSS custom properties are still named `--teal-*` and `--gold-*` for historical reasons (the original handball crest was teal/gold), but during the basketball rebrand their *values* were repointed to navy/red to match the new SGTBL crest. Don't assume the variable name tells you the color — check the actual hex value.
- Team accent colors (`--team-knicks-bg`, `--team-eagles-bg`, etc.) are unrelated to league branding — just per-team decorative colors, untouched by the rebrand.
- **CSS comment gotcha (bit us once):** never write a literal `*/` sequence inside a `/* ... */` comment (e.g. writing `--teal-*/--gold-*` as shorthand) — it silently closes the comment early and can corrupt/drop everything up to the next `*/`, with no console error. If colors suddenly stop resolving, check computed styles (`getComputedStyle(document.documentElement).getPropertyValue('--brand')`) before assuming it's a caching or logic issue.
- **Dark mode — now site-wide, public site included** (user asked 2026-11-15, reversing the earlier portal-only scope). On the public site the sun/moon toggle is injected into `.site-nav .nav-actions` (before the mobile menu button); same `sgtbl-theme` localStorage key, so the choice carries across public + portals. Public-only dark fixes are at the end of `site.css` (nav toggle colors, selected tab, `.eyebrow`/`.card-link`/sort-caret → `--teal-200`, winning scores → `--text-primary`, standings loss streak lighter red) — found by a contrast audit of all 10 public pages. `.btn-accent` (red buttons) now uses white text site-wide (6.8:1; was navy ink at 2.7:1 — user approved 2026-11-15). Still-known miss in both themes: the red "27" score in the homepage hero card. Older portal-only details below still apply: Toggled via a sun/moon button, injected into every `.admin-topbar` at runtime by `interactions.js` (not hand-added per page) — a manual toggle with the choice persisted to `localStorage` under `sgtbl-theme`, shared across both portals since it's the same person. Mechanics:
  - Dark values live in `tokens.css` under `:root[data-theme="dark"]`, overriding the semantic tokens (`--surface`, `--surface-alt`, `--surface-sunken`, `--text-primary`, `--text-muted`, `--border`, `--border-strong`, `--brand-strong`) plus the three light-end neutral scale steps (`--slate-50/100/200`) that a handful of components (`.pctl-chip.pctl-50`, button hover states) reference directly instead of through a semantic token. `--slate-50/100/200` are kept *lighter* than `--surface` in the dark palette on purpose — early draft made them darker than `--surface`, which made "highlighted chip" components (e.g. the neutral percentile chip) nearly invisible against their own card.
  - `--brand` itself is deliberately **not** overridden (only `--brand-strong` is) — `--brand` doubles as `.btn-primary`'s background with white text on top; flipping it lighter for dark mode would make that text illegible. `--brand-strong` is text-only usage (headings, stat values), safe to lighten.
  - (Superseded 2026-11-15 — the public site now has the toggle too.) The old scoping trick: interactions.js only injected the toggle (and only ever set `data-theme`) when `.admin-topbar` existed on the page — an element that only exists in portal chrome, never on the public site. So even though `tokens.css`/`base.css` are loaded site-wide and a few dark overrides touch classes public pages also use (e.g. `.tabbar`, defined in `site.css` but reused by the portals), the public site can never actually end up in `data-theme="dark"` and is unaffected. That audit has now been done (see above).
  - The plain neutral `.badge` (no color variant, e.g. draft-pool "Pool" tags) needed a dedicated dark override in `base.css` (`:root[data-theme="dark"] .badge:not([class*="badge-"])`) since it hardcodes `--slate-100`/`--slate-700` as a bg/text pair rather than using semantic tokens — flipping the scale alone would've made it dark-on-dark. The colored badge variants (`.badge-success` etc.) were left alone deliberately — their light-bg/dark-text pairing is self-contained and reads fine as a bright chip regardless of page theme, same pattern GitHub and others use.
  - `body.admin`'s background was changed from a raw `var(--slate-100)` to the semantic `var(--surface-alt)` so it actually responds to the theme (one-shade difference in light mode, imperceptible).
  - Known gap: a few raw `--slate-300/500/600/700/900` references elsewhere (icon tints, marker lines, a couple of hover border-colors) were deliberately left un-themed since they're mid-tone enough to stay legible in both themes — don't assume every raw slate reference needs a dark override, check contrast before "fixing" one.

## Rules that shape the UI (don't relitigate these without re-reading the doc)

- **No salary cap (decided 2026-11-15).** The cap-points economy, player salaries, contracts/contract lengths, the 70% floor, Min/Max/Current Cap, and reserve-list cap charges were all removed. Don't reintroduce any of it.
- **FAAB** is the only in-season currency: **$100 per team per season**, resets each season (no carryover), sealed blind bids, **$1 minimum bid**, ties go to the team with the worse record, can't be traded. Nominating a player commits the nominator to a $1 bid if nobody else bids. Winning bid amounts are shown to the winning team + League Admin only (outcome is public).
- **Trades are player-for-player** and are called **"Trades"** everywhere (the old Trade→Transfer rename plan is cancelled). Each side must send ≥1 player; counts don't have to match (2-for-1 is fine) as long as both teams stay within **9 active / 3 reserve**. No FAAB, cap points, or draft picks in trades (user confirmed picks stay out "for now" — may revisit). Both captains confirm, then **League Admin approves** every trade. A reserve player arrives on the receiving team's reserve list unless "Activate on arrival" is checked.
- **Reserve List** stays, at no cost: up to 3 players per team, off the 9-man active roster, rights retained.
- **Playoffs exist** (top 3 of 6 teams; regular season is 15 games/team). Standings has a dashed playoff-cutoff line after 3rd place. Tiebreaker order: point differential → total points → head-to-head → coin flip.
- Regular-season games can end in a tie (no OT); **playoff games cannot** (5-minute OT periods). No playoff bracket format is implemented yet — the source doc itself leaves bracket/seeding TBD.
- Season 1 draft is an **auction** (every player nominated one at a time, captains bid) — not a snake/timed pick-order draft. Bids come from a **one-time draft-only budget** (**$1,000 per team**, confirmed by the user) that vanishes after the draft and is unrelated to FAAB. Draft bidding is open and incremental (user, 2026-11-21): everyone sees the high bid; raises of $1/$5/$10 by price tier; each bid tops the clock up to 10 s. Draft prices display as dollars (`$140`), never "pts". Season 2+ uses a straight order for the top half and a weighted lottery for the bottom half (not yet built).

## Working conventions established so far

- The user finds large, unbounded change lists overwhelming — when auditing against a rules doc, present findings in tiers/priority order and let them pick what to tackle, rather than fixing everything at once.
- Prefer fixing things at the design-token level (CSS variables) over hunting down individual hardcoded values, when a rebrand or palette change is involved — it's lower risk and touches fewer files.
- After any visual change, verify by loading the page through the local server and checking computed styles / screenshots — don't trust that an edit "worked" just because the diff looks right. **Specifically:** `getComputedStyle().gap` can report a value even when the element isn't actually a flex/grid container (e.g. a `<td>` defaulting to `display:table-cell`) — verify layout properties with real pixel measurements (`getBoundingClientRect()` on the elements in question), not just the declared CSS property.
- Watch for CSS variables that don't exist in the token scale (e.g. `--slate-400` was referenced but the scale jumps 500→300) — these fail silently (transparent/inherited), no console error.
- Never write a literal `*/` inside a CSS comment (e.g. shorthand like `--teal-*/--gold-*`) — it closes the comment early and can silently drop everything up to the next real `*/`.
- When the user states a number/formula that contradicts a value already established elsewhere on the same page (or the rules doc), say so and show the derivation rather than silently applying it — this has come up multiple times and the user has responded well to being shown the math rather than just complying. That said, when the user reconfirms a specific number after seeing the flag, implement exactly what they asked even if a residual question remains — flag it for the record, don't block on it.
- Build order preference: **admin-side portals first, public site second.** Within the admin side, Captain Portal was built before finishing League Admin cleanup, and within Captain Portal, `my-team.html` was taken to near-final polish before moving to sibling pages — the user wants each page "perfected" one at a time rather than broad shallow passes across everything at once.
- When a role/permission split matters (e.g. captain vs. admin), model it as genuinely separate pages/nav/persona, not a shared shell with conditionally-hidden items — reflects real permission boundaries even without real auth.
