# SGTBL — Church Basketball League Platform (prototype)

Static visual prototype for **St. Gabriel Team Basketball League (SGTBL)** — a public-facing league site plus a captain/admin portal. Originally scoped as a **team handball** league (SGTHL); the sport changed to basketball partway through the project. If you see anything referencing handball, goals, goalkeepers, or the old teal/gold branding, it's leftover from before the switch and should be treated as a bug, not a feature.

## What this is (and isn't)

A **static HTML/CSS/JS prototype** — no backend, no database, no real auth, no payment processing. All data (teams, players, stats, transactions, schedule) is sample/fictional, hand-written into the HTML. The goal is to validate look, feel, and information architecture before committing to a real tech stack.

**Two separate authenticated personas, matching real permission boundaries** (this was a deliberate split, not a shortcut): League Admins run league operations (schedule, scorekeeping, transaction approval, data sync, publishing) and never see a captain's private roster/cap details beyond what they're approving. Captains manage only their own team (roster, weekly availability, transfer proposals, free-agency bids, scouting, film) and never see admin-only tools. Don't merge these back into one shared nav — the separation is intentional.

## Design system notes

- Fonts: Barlow Condensed (headings/display) + Inter (body), loaded from Google Fonts.
- Brand palette lives in `tokens.css`. **Gotcha:** the CSS custom properties are still named `--teal-*` and `--gold-*` for historical reasons (the original handball crest was teal/gold), but during the basketball rebrand their *values* were repointed to navy/red to match the new SGTBL crest. Don't assume the variable name tells you the color — check the actual hex value.
- Team accent colors (`--team-lions-bg`, `--team-eagles-bg`, etc.) are unrelated to league branding — just per-team decorative colors, untouched by the rebrand.
- **CSS comment gotcha (bit us once):** never write a literal `*/` sequence inside a `/* ... */` comment (e.g. writing `--teal-*/--gold-*` as shorthand) — it silently closes the comment early and can corrupt/drop everything up to the next `*/`, with no console error. If colors suddenly stop resolving, check computed styles (`getComputedStyle(document.documentElement).getPropertyValue('--brand')`) before assuming it's a caching or logic issue.
- **Dark mode — Captain Portal & League Admin only, not the public site** (deliberate scope; user confirmed this explicitly). Toggled via a sun/moon button, injected into every `.admin-topbar` at runtime by `interactions.js` (not hand-added per page) — a manual toggle with the choice persisted to `localStorage` under `sgtbl-theme`, shared across both portals since it's the same person. Mechanics:
  - Dark values live in `tokens.css` under `:root[data-theme="dark"]`, overriding the semantic tokens (`--surface`, `--surface-alt`, `--surface-sunken`, `--text-primary`, `--text-muted`, `--border`, `--border-strong`, `--brand-strong`) plus the three light-end neutral scale steps (`--slate-50/100/200`) that a handful of components (`.cap-util-track`, `.term-bar-track`, `.pctl-chip.pctl-50`, button hover states) reference directly instead of through a semantic token. `--slate-50/100/200` are kept *lighter* than `--surface` in the dark palette on purpose — early draft made them darker than `--surface`, which made "highlighted chip" components (e.g. the neutral percentile chip) nearly invisible against their own card.
  - `--brand` itself is deliberately **not** overridden (only `--brand-strong` is) — `--brand` doubles as `.btn-primary`'s background with white text on top; flipping it lighter for dark mode would make that text illegible. `--brand-strong` is text-only usage (headings, stat values), safe to lighten.
  - The scoping trick: interactions.js only injects the toggle (and only ever sets `data-theme`) when `.admin-topbar` exists on the page — an element that only exists in portal chrome, never on the public site. So even though `tokens.css`/`base.css` are loaded site-wide and a few dark overrides touch classes public pages also use (e.g. `.tabbar`, defined in `site.css` but reused by the portals), the public site can never actually end up in `data-theme="dark"` and is unaffected. Don't add a public-site toggle without re-auditing which site.css components would then need their own dark variants.
  - The plain neutral `.badge` (no color variant, e.g. draft-pool "Pool" tags) needed a dedicated dark override in `base.css` (`:root[data-theme="dark"] .badge:not([class*="badge-"])`) since it hardcodes `--slate-100`/`--slate-700` as a bg/text pair rather than using semantic tokens — flipping the scale alone would've made it dark-on-dark. The colored badge variants (`.badge-success` etc.) were left alone deliberately — their light-bg/dark-text pairing is self-contained and reads fine as a bright chip regardless of page theme, same pattern GitHub and others use.
  - `body.admin`'s background was changed from a raw `var(--slate-100)` to the semantic `var(--surface-alt)` so it actually responds to the theme (one-shade difference in light mode, imperceptible).
  - Known gap: a few raw `--slate-300/500/600/700/900` references elsewhere (icon tints, marker lines, a couple of hover border-colors) were deliberately left un-themed since they're mid-tone enough to stay legible in both themes — don't assume every raw slate reference needs a dark override, check contrast before "fixing" one.

## Rules that shape the UI (don't relitigate these without re-reading the doc)

- **No individual player salary/cap-points values are ever public.** Team pages show a payroll *total* only. Completed transfer fee amounts *are* public (the rules doc explicitly allows announcing that a transfer happened and its point cost), but the underlying per-player valuation never is.
- **Cap Points vs. game points**: "cap points" (roster/auction currency) must stay visually and terminologically distinct from a team's or player's actual game score, especially now that the sport is basketball and game scores are *also* called "points." Prefer explicit labels ("Cap Points" vs "PTS") over bare "points" wherever ambiguous.
- **Playoffs exist** (top 3 of 6 teams; regular season is 15 games/team). Standings has a dashed playoff-cutoff line after 3rd place. Tiebreaker order: point differential → total points → head-to-head → coin flip.
- Regular-season games can end in a tie (no OT); **playoff games cannot** (5-minute OT periods). No playoff bracket format is implemented yet — the source doc itself leaves bracket/seeding TBD.
- Season 1 draft is an **auction** (every player nominated one at a time, captains bid) — not a snake/timed pick-order draft. Season 2+ uses a straight order for the top half and a weighted lottery for the bottom half (not yet built).

## Cap-points economy model (nailed down on `site/captain/my-team.html` Payroll tab — treat this as the reference implementation)

This took several rounds to get right; don't re-derive from scratch, and don't re-litigate without re-reading Section 5.F / 6.A–6.C of the basketball rules doc.

- **Baseline (900)** — universal, fixed. 100 cap points × 9 active roster spots (season-one assumption). Everything below derives from this one number.
- **The 15% cushion is gone (amendment, superseding the old two-stage Base Cap/Max Cap model below this baseline)**: there is no more separate fixed "Base Cap" starting point stacked on top of the baseline. A team's **Current Cap** now starts at the baseline (900) itself and moves within a single symmetric **±15% band — 765 to 1,035** — via transfers over the season. **Min Cap (765)** = 900 × 0.85; **Max Cap (1,035)** = 900 × 1.15. (Historical note: 1,035 happens to be the same number the old "Base Cap" used — that's a coincidence of both being 900 × 1.15, not a sign anything carried over conceptually. The old band was the asymmetric 900–1,170, i.e. baseline-plus-two-stacked-15%-cushions; that's fully retired.)
- **70% Floor (630)** — **fixed for the season**, untouched by the cushion removal. Locked at 70% of the fixed **900 baseline** (900 × 0.7 = 630) — not 70% of Current Cap, not 70% of Max Cap. A team can trade its way toward the 1,035 ceiling and still only be required to deploy 630 on the active roster — legal, just a poor allocation of the extra room. This is a different question from the 765–1,035 band: the floor governs how much must stay deployed on the **active roster**; the band governs how far the team's overall working-budget ledger can drift.
- **Pts Spent (923)** — sum of active-roster players' individual cap values (882) **plus** the Year-1 50% reserve charge on any reserve player still in their first season on reserve (currently 26 for Grace Bennett + 15 for Nate Price = 41; see the Reserve List rule below). Must stay ≥ 630 (the floor) at all times.
- **Reserve List cap rule (amendment — reserve salaries do *not* uniformly sit at 0%)**: a captain choosing to hold a player's rights on reserve (instead of releasing him) pays for it — for the season that player first goes to reserve, 50% of that year's salary still counts against Pts Spent/the 70% floor, same as an active player's. Only once that season ends does the contract freeze completely (0% counting, years paused) at whichever contract year it stopped on, staying inert until reactivated. Both current reserve players (Grace Bennett, Nate Price) are still in that first charged season, so both currently count at 50%.
- Stat tiles on the Cap Utilization card: Current Cap (970, a mid-band example value — deliberately not equal to either Pts Spent or Max Cap, so nothing on the bar visually collides), Pts Spent (+ remaining/% under Current Cap), Available to Acquire, Available to Sell.
- **Unresolved directional flag, deliberately left as-is**: the rules doc says selling a player *adds* points to a team's ledger (pushes Current Cap toward Max Cap) and acquiring *subtracts* (pushes toward Min Cap). Read literally, "Available to Sell" should pair with the Max Cap ceiling and "Available to Acquire" with the Min Cap floor — the reverse of what's currently implemented (Available to Acquire = Max Cap − Current Cap; Available to Sell = Current Cap − Min Cap). The user asked for it this way twice after the flag was raised, so it's implemented as instructed — worth a clean second look before building the same pattern anywhere else (e.g. League Admin's Economy page). Watch this especially if Current Cap is ever set to sit exactly at Min Cap or Max Cap in a future sample update — the backwards labeling becomes glaringly obvious at either extreme (e.g. "Available to Acquire: 0" while sitting at the ceiling, when intuitively the team can still acquire plenty from there).
- The bar's fill color is state-driven: `.status-ok` (green) when compliant, `.status-violation` (red) when a team is under the floor or Current Cap is out of its allowed range — only the green state has been exercised so far (Lions are compliant). The track has four marks now: Floor (630, red), Min Cap (765, slate — CSS class `.mincap`), Current Cap (970, **`--accent-blue`**, a new theme-agnostic token — CSS class `.currentcap`, renamed from the old `.basecap` since that concept no longer exists), Max Cap (1,035, gold). Keep Current Cap's example value clear of both the fill's right edge and the Max Cap mark — labels collide/garble at ~3% track separation or less (learned the hard way: 1,000 sat 3.4% from 1,035 and the two labels overlapped into unreadable text).
- **Track scale doesn't start at 0** — the four marks' inline `left:%` values (and the fill's `width:%`) are computed against a **550–1,035** range, not 0–1,035. All four meaningful values (630/765/970/1,035) sit in a fairly narrow band, so scaling from literal 0 crammed them into the right ~40% of the bar; 550 was chosen as a floor just below the 630 Floor mark, giving every mark room to breathe while keeping Max Cap pinned at the right edge (`right:0`, unchanged convention). If any of these four numbers change, recompute all four `left:%`/`width:%` values against `(value − 550) / (1035 − 550)`, not against `value / 1035`.
- **`--accent-blue` (`#3b82f6`)** — a new token in `tokens.css`, added specifically because `--teal-600`/`--teal-700` (Current Cap's original color) are calibrated for dark-text-on-light and become nearly invisible on the dark-mode surface. Rather than patch it with a dark-mode-only override (the pattern used elsewhere in this file), the color itself was replaced with something vivid enough to read in both themes without a `:root[data-theme="dark"]` override at all — reach for this pattern (a theme-agnostic replacement) before reaching for a dark-only patch when an element's *only* use is decorative/informational (not paired with must-match text like `.btn-primary` is with `--brand`).
- Layout: Contract Grid (left, content-width table) sits beside a right-hand column (`.contract-grid-row`, CSS Grid `auto minmax(300px,1fr)`, `align-items:start` — deliberately *not* `stretch`, which previously forced the shorter column's box to stretch and leave ugly blank filler) containing, top to bottom, the **Reserve List** card then the **Cap Points by Position** donut card. Both cards got their old explanatory paragraphs moved into a small hover/focus info-tooltip (`.info-tip`/`.info-icon`/`.info-tooltip` in `base.css`) next to the card title, to keep the column compact. The donut's total (923) and its Center/Shooting Guard slices include the two reserve players' 50% charges, not just the 9 active players.

## Working conventions established so far

- The user finds large, unbounded change lists overwhelming — when auditing against a rules doc, present findings in tiers/priority order and let them pick what to tackle, rather than fixing everything at once.
- Prefer fixing things at the design-token level (CSS variables) over hunting down individual hardcoded values, when a rebrand or palette change is involved — it's lower risk and touches fewer files.
- After any visual change, verify by loading the page through the local server and checking computed styles / screenshots — don't trust that an edit "worked" just because the diff looks right. **Specifically:** `getComputedStyle().gap` can report a value even when the element isn't actually a flex/grid container (e.g. a `<td>` defaulting to `display:table-cell`) — verify layout properties with real pixel measurements (`getBoundingClientRect()` on the elements in question), not just the declared CSS property.
- Watch for CSS variables that don't exist in the token scale (e.g. `--slate-400` was referenced but the scale jumps 500→300) — these fail silently (transparent/inherited), no console error.
- Never write a literal `*/` inside a CSS comment (e.g. shorthand like `--teal-*/--gold-*`) — it closes the comment early and can silently drop everything up to the next real `*/`.
- When the user states a number/formula that contradicts a value already established elsewhere on the same page (or the rules doc), say so and show the derivation rather than silently applying it — this has come up multiple times (a "915" baseline, an "880" floor) and the user has responded well to being shown the math rather than just complying. That said, when the user reconfirms a specific number after seeing the flag, implement exactly what they asked even if a residual directional question remains (see the sell/acquire flag above) — flag it for the record, don't block on it.
- Build order preference: **admin-side portals first, public site second.** Within the admin side, Captain Portal was built before finishing League Admin cleanup, and within Captain Portal, `my-team.html` was taken to near-final polish before moving to sibling pages — the user wants each page "perfected" one at a time rather than broad shallow passes across everything at once.
- When a role/permission split matters (e.g. captain vs. admin), model it as genuinely separate pages/nav/persona, not a shared shell with conditionally-hidden items — reflects real permission boundaries even without real auth.
